# 移除闲时任务入口 (offpeak-removal)

## 背景

上游的「闲时任务」（off-peak / idle-time task）是：用户提出一个可以延后做的事，应用先向**云端取号**排队，
之后由云端在它认为空闲时授予算力，桌面端在原会话里无人值守地跑完，不占套餐额度。

本 fork 正在做的事是**去掉云账号与 Coding Plan 体系**（见 `FEATURES.md` 的 `local-mode` 条目）：用户只用
自定义服务提供商。在这个前提下闲时任务**永远无法创建**，因为它的两个前置条件都不存在：

- 取号走云端票据服务（`POST /ticket`）；
- 创建资格要求账号有符合条件的 Coding Plan 连接。

但它仍然以两种方式留在产品里：

1. **模型上下文**：只要宿主下发了 `offPeakToolEnabled` 灰度开关，`OffPeakCreate` / `OffPeakList` 就会注册进
   工具面——两个工具定义（描述 + 每条 8 行的模型指令 + JSON Schema）会进入**每一次**模型请求。实测本机会话
   的工具面里就有它们（156 个工具中的两个），而这些 token 买来的是一个必然失败的工具。
2. **可达的入口**：模型看得到、有可能去调，调了必然报「没有可用连接 / 服务不可达」，用户看到的是无意义的失败。

所以本次目标：**让闲时任务在模型面前彻底消失，并让它的执行路径不可达**。

## 规则

1. **闲时工具永不注册**：`OffPeakCreate` / `OffPeakList` 不进入工具注册表，因此不进入 provider 工具面。
   这个保证**与云端灰度开关无关**——不是「开关关了所以没有」，而是「没有再能被打开的门」。
2. **闲时任务无法创建**：宿主不再创建/注入创建端口，创建路径整体不可达。
3. **其余实现保留为死代码**（用户明确接受）：不删除服务层、UI、协议字段、数据库表、运行时里的闲时轮判定逻辑。

### 为什么是「掐入口 + 留死代码」而不是全量删除

- **fork 纪律**：删得越多，上游同步的冲突面越大。本仓库对上游能力的一贯处理是「入口屏蔽，不删除代码」，
  `local-mode` 走的也是这条路（FEATURES.md 原文：「入口屏蔽，不删除代码」）。
- **面太大**：闲时任务横跨 6 个包、50+ 文件（UI 的自动化页面与闲时编辑/历史视图、服务层 RPC 与仓库、
  桌面调度器的领号/派发/结算、shared 协议 schema 与遥测字段、CLI 运行时）。全量删除会把协议 schema 与
  整个 UI 卷进来，收益低、回归风险高，且与「本地模式」的批次边界混在一起。
- **代价可接受**：留在 bundle 里的不可达代码不占模型上下文、不影响运行时行为。

### 保留部分的现状（为什么已经是死路）

| 保留的东西                                                                                        | 为什么不可达                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core` 的 `off-peak.ts` handler、contracts 里的输入/输出 schema、`OffPeakPort` 类型与上下文透传   | 没有任何注册路径引用它们（注册表是唯一入口），端口也不再被注入                                                                                                                                              |
| 协议命令字段 `offPeakTaskId` / `offPeakRunType` / `offPeakToolEnabled`、`off-peak-tool-policy.ts` | 这些是「云端派发 / 云端开关」的入口；本 fork 无云账号，不会被下发，且其下游（工具面）已移除                                                                                                                 |
| UI：自动化页面的闲时区块、`useOffPeakEligibility`、`offPeakTaskStore`、编辑器/历史/通知           | 创建入口同时受云端灰度配置（`offPeakGrayConfig.enabled`）与 Coding Plan 资格（`codingPlanSupport.supported`）门控；本 fork 下前者拿不到、后者为否，创建入口处于禁用态（有历史任务时列表仍可见，但不能再建） |
| 服务层（`offPeakTaskService` / repo / server client / gateway）、桌面调度器（领号、派发、结算）   | 只有云端下发票据时才有事可做                                                                                                                                                                                |
| 运行时里的闲时轮身份与 denylist（`isOffPeakCreateRestrictedTurn` 等）                             | 判定的对象（闲时派发轮）不会再出现。已核对：它与 automation 轮身份互斥，保留不影响正常轮与定时任务轮                                                                                                        |

## 边界与已知后果

- **不清理历史数据**：数据库里已有的闲时任务记录保持原样，不做迁移；UI 上如果还有未终态任务，列表仍会显示（只是不能再创建）。
- **不做协议兼容处理**：云端若仍下发 `offPeakToolEnabled: true`，现在是无效果（以前是开工具面）；协议字段保留，
  不报未知字段错误。这符合「本 fork 不接云端」的既有前提。
- **不恢复**：将来若重新接入云端账号体系，需要把三处入口按本文档恢复（见实现文档第 2 节的逐处清单）。

## 验收场景

| #   | 场景                                                          | 期望                                           |
| --- | ------------------------------------------------------------- | ---------------------------------------------- |
| 1   | 常规装配（默认 options）                                      | 注册表里没有 `OffPeakCreate` / `OffPeakList`   |
| 2   | 把所有可选工具面开关都打开                                    | 仍然没有这两个工具（它们不再有任何开关）       |
| 3   | 从注册表取 provider 契约（即模型请求里的 `tools`）            | 契约名列表里不出现这两个名字                   |
| 4   | 宿主要求开启闲时工具（老协议字段 `offPeakToolEnabled: true`） | 无效果：工具面依旧没有它们                     |
| 5   | 现有其它工具面                                                | 不受影响（数量与内容除这两个之外与改动前一致） |

## 验证方式

- 单测 `apps/zcode-cli/packages/core/test/forkOffPeakRemoval.test.ts`：
  场景 1–3 用真实注册表断言；另外对「注册表文件里不再出现任何 OffPeak 引用」做源码级不变量断言
  （上游把条目加回来会直接红）。
- 守卫 `scripts/check-fork-removals.mjs`：新增「路径作用域的必须缺席」规则，钉住三处入口
  （注册表文件不得出现 OffPeak、运行时工具装配不得出现 `includeOffPeak`、协议宿主不得创建闲时端口）。
- 运行期：新会话的模型请求里 `tools` 不含 `OffPeakCreate` / `OffPeakList`
  （本机 `~/.zcode/cli/debug/model-io-*.jsonl` 可直接核对）。
